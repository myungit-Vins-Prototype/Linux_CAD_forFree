## Contratto ed esportazioni

- `CadViewport` e un widget dichiarato interno (`forgeCad2026_viewport.h:80`); i dieci metodi sono pubblici ordinari, non virtuali/slot/Q_INVOKABLE. `DrawingSheetEditor` ha analogo metodo ordinario. Nessuno dei simboli liberi usa macro export negli header esaminati.
- `CMakeLists.txt:116` costruisce l'eseguibile; `:469` installa soltanto il runtime del target forgecad. Le altre installazioni sono desktop/MIME/icone. `kernel/CMakeLists.txt:15` costruisce forgekernel STATIC. Nessuna regola PUBLIC_HEADER/EXPORT/SDK o libreria condivisa di queste API trovata nei CMake attivi. Non e una prova sull'ABI del binario o su consumatori fuori repository: nessun nm/linker/garbage-collection nuovo eseguito.
- Getter e cataloghi conservati diventerebbero API intenzionali per decisione esplicita; questo audit non sostiene che lo fossero storicamente. Le quattro rimozioni proposte richiedono comunque decisione sul contratto pubblico e verifiche successive prima di intervenire.

## Pulizie che richiedono un delta coerente

- Callback Estendi: setter, `extendPickFinished_` e ramo legacy sono una piccola catena. Conservare `beginExtendPick`, `edgePickExtend_`, `edgePickLinear_`, `requestExtendPreview` e callback changed/key attivi. Le tre deprecazioni non autorizzano a rimuovere il picker.
- Provider tavola: `DrawingWindow` nasconde il comando via findChild e dereferenzia il risultato. Togliere il comando interno senza aggiornare quel punto introdurrebbe un errore; aggiornare invece il setter da solo lascerebbe il resto morto. Il percorso da .prt salvato e quello attivo.
- Camera: omonimi di ViewportCamera chiamati in produzione e test restano distinti dai due wrapper orfani. Analogamente sketchesOf, firstRayHit, stato snap/sezione, nomi persistiti e strumenti Fix non sono orfani per propagazione.
